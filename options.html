The extension only needs to read workflow runs. Use a fine-grained token with read-only access: it cannot change anything on GitHub, even if it leaked.

  1. Create a read-only token on GitHub Opens GitHub's form with the name, a 90-day expiry and Actions: Read-only already set (Metadata: Read-only is added automatically).
  2. Under Repository access, choose All repositories (or only the ones you want to monitor). For an organization's repositories, pick it as the Resource owner; some organizations must approve tokens first.
  3. Click Generate token, copy it, paste it below and click Save Token. The extension checks it right away.

A classic token also works (it needs the repo scope for private repositories), but that scope grants full read and write access to all of your repositories, so a fine-grained token limited to Actions is safer.

When enabled, your GitHub token will be synchronized across all your Chrome instances where you're signed in. The token will be stored on Google's servers (encrypted in transit). Default: OFF for privacy. Your repositories and settings are always synced.

🚀 Add repositories

  1. Click the extension icon to open the popup, then + Add. On a repository's GitHub page the popup offers it right away: click Add it.
  2. Type an Owner: your GitHub username or an organization. Owners you have used are remembered and offered when you click the field.
  3. Pick a Repository from the dropdown: every repository of that owner your token can see, private ones included.
  4. Select a branch: "All branches" or a specific one.
  5. Click "Add Repo", then watch the icon: its color and number cover every monitored repository.

Polling Interval

How often to check for updates when all workflows are stable (completed/failed). When workflows are running, polling automatically speeds up to 5 seconds.

Adaptive Smart Polling:
  • Normal mode uses your selected interval for efficient API usage
  • When ANY workflow is running or queued, switches to 5-second polling
  • Returns to normal interval once all workflows complete
  • Chrome runs background checks at most every 30 seconds, so 30 seconds is the shortest normal interval

🔔 Notifications

Get desktop notifications when workflow status changes.

When enabled, you'll receive a notification when a workflow status changes (starts, completes, fails). Notifications include:

  • Repository name (owner/repo)
  • Workflow name and status
  • Colored icon matching the status (🟢 green, 🟡 yellow, 🔴 red)
  • Click to open workflow run directly in GitHub
  • Smart filtering: only on status changes, skips errors and first poll
  • Higher priority for failures

Enabled by default. Preference syncs across devices.

API Usage

GitHub allows 5,000 API requests per hour. The extension asks GitHub "has anything changed?" with each check (a conditional request): when nothing has, GitHub answers "304 Not Modified", which does not count against the limit. So most checks are free, even during 5-second fast polling.

📖 How It Works

GitHub Actions Monitor tracks the status of your GitHub Actions workflows across multiple repositories and provides real-time visual feedback through a dynamically colored extension icon.

🎨 Icon Colors

Yellow (Highest Priority)

One or more workflows are currently running or queued

Green (All Success)

All monitored workflows have passed successfully

Flashing Red/Green (Mixed)

Some workflows succeeded, others failed (flashes every 1 second)

Red (All Failed)

All monitored workflows have failed

Gray

No repositories configured, no data available, or error

The number on the icon counts failing repositories in red, or running ones in amber when nothing fails (Monitoring tab: change or turn off). Hover the icon for both counts.

⚡ Adaptive Smart Polling

The extension intelligently adjusts its polling frequency based on workflow activity to provide near real-time updates when you need them most, while conserving API requests when workflows are stable.

🐢 Normal Mode

When all workflows are in a stable state (completed, failed, or no workflows):

  • Polls at your configured interval (default: 30 seconds)
  • Efficient API usage for long-term monitoring
  • Suitable for watching multiple repositories

🚀 Fast Mode (Automatic)

Automatically activates when ANY repository shows a yellow icon (workflow running or queued):

  • Switches to 5-second polling
  • Provides near real-time updates on workflow progress
  • Catches workflow completions almost instantly
  • Automatically returns to normal mode once all workflows complete or fail

💡 Example: You push code triggering a workflow. The icon turns yellow and polling speeds up to 5 seconds. When your workflow finishes (green or red), polling automatically returns to your configured interval.

🔄 How Status is Determined

For each monitored repository (and branch), the extension looks at the latest run of every workflow, not just the newest run, so a failing CI is never hidden by a deploy that finished after it. A repository is yellow if any workflow is running, red if any workflow's latest run failed, and green when they all passed. Cancelled and skipped runs are shown but never turn a repository red. The popup lists each workflow with its state and timing. The icon color reflects the highest priority status across all repositories:

Priority Order: Yellow (in-progress) > Green (all success) > Mixed (flash red/green) > Red (all failed) > Gray (no data)

📦 Repository Features

👤 Owner and Repository Picker

Adding a repository takes an owner and a pick from a list:

  • Type an owner: your GitHub username or an organization
  • The Repository dropdown lists every repository of that owner your token can see, private ones included
  • Private, archived and already monitored repositories are labelled
  • Owners you have added repositories from are remembered (and synced) and offered when you click the field
  • The last owner you used is filled in the next time you open the popup

🌿 Per-Branch Monitoring

Monitor specific branches of your repositories:

  • After entering a repository, select which branch to monitor
  • Choose "All branches" to monitor any workflow activity
  • Or select a specific branch (e.g., main, develop, production)
  • Monitor the same repository on multiple branches simultaneously
  • Each repo+branch combination tracked independently

🗂 Compact Cards

Each repository is two lines; the details are a hover or a click away:

  • Line one: the repository, its branch, and a "Review" marker when a run waits for a review or approval
  • Line two: the state, where a failure happened ("Test › npm test") and the run's timing
  • Hover: every workflow's state, and the commit, pull request and author of the latest run
  • The chevron expands a card: run context, every workflow with its last ten runs as a strip of bars, and a link to the failed job's log
  • A failed workflow quotes the lines from its log that say why, so you often do not need to open GitHub
  • Step lights: a running workflow lights a light per step as each finishes (the running one pulses) and names the step it is on; a failed one shows where it stopped
  • Keep it in view: the buttons at the top dock the popup into the side panel (stays open while you browse), pop it out into its own window, or (from those) keep it on top of every other window
  • The counts above the list filter it: click the red one to see only what is failing

🔕 Ignoring a Workflow

Every workflow in an expanded card has a switch:

  • Off: the workflow stays listed (dimmed) but never turns the repository red or yellow
  • It is left out of the counts, the badge and notifications
  • Useful for scheduled jobs, CodeQL, Dependabot or anything else noisy
  • Kept per repository and branch, and synced

↻ Re-run and Cancel (optional)

Off by default, so the extension only reads. Turned on (Setup, Choose features):

  • Failed workflows get a re-run button (re-runs the failed jobs)
  • Running workflows get a cancel button (asks first)
  • The token needs Actions: Read and write. Chosen before the token, the token link asks for it. With a token already saved, Setup checks it (by asking to cancel a run that already finished, which GitHub declines; nothing is cancelled) and, only if it is missing, shows how to add it to that token on GitHub
